There is a category of UI work that developers know they could build, but do not.

Not because it is too hard. Because the iteration cost is too high.

Spark changes that calculation.

## The Threshold Problem

Every ambitious UI idea hits a threshold: the point where the exploration cost outweighs the likely payoff.

An MC Escher-inspired 3D splash screen with animated tessellation. A neural network visualizer with animated weight flows. A particle system that responds to scroll position.

You know these are possible. You might know how to build them. But the gap between "possible" and "good" requires iteration, and iteration takes time.

With slow tooling: ten iterations might take an afternoon. You do two, pick the better one, ship something mediocre.

With Spark: ten iterations take ten minutes. You find the actually good version.

## What I Actually Built

Neural network visualization. Real topology — layers, nodes, weights — with animated connections that update as data flows.

The interesting part was not the implementation. It was the iteration on the visual language.

How thick should the weight connections be? Should they animate continuously or on trigger? How do you represent negative weights?

These are not engineering questions. They are design questions. You can only answer them by seeing it.

I ran eight variations in the time it would have taken to build one complete version with standard tooling. Found an approach I would not have thought to try if I had been constrained to one or two attempts.

## Nobody Does This With Standard Tooling

Exact quote from my notes: "Nobody does this with Claude Code or Codex. It would take minutes. With Spark it is seconds."

These experiences are not uniquely possible with Spark. They are uniquely practical.

The MC Escher splash screen: I could have built that with any capable model. But would I have? Not as a prototype. The cost is too high.

With Spark, throwaway exploration is affordable. The first four versions were bad. The fifth was interesting. The seventh was the one I kept.

## The Creativity Effect

When iteration is expensive, you are conservative. You reach for familiar patterns. You implement something you have seen work before.

When iteration is cheap, you try things you are not sure will work. You pursue the interesting idea even if you do not know how it will land.

That shift in risk tolerance is where novel experiences come from.

I have built things with Spark that I would have dismissed as too speculative with slower tooling. Some did not work. But enough did that the exploration was worth it.

## What I Would Tell You

1. **The threshold has moved.** What was impractical is now practical.

2. **Iteration cost was the bottleneck, not capability.** You could always build these things. You could not afford to find the good version.

3. **Risk tolerance shifts.** When trying costs nothing, you try more things.

4. **The best experiences come from exploration.** Not from the first thing you think of.

## The Practical Pattern

The experiences worth attempting with Spark are ones where:

1. The quality bar is high — you need the actually good version.
2. Evaluation requires seeing, not reasoning.
3. The interesting design lives in the iteration space.

If all three are true, Spark unlocks work that is otherwise impractical.

Start with an ambitious spec. Generate five variations without judging them. Look at all five. Notice what works. Generate five more.

You will find things you were not looking for. That is the point.

With slow tooling, you build what you planned. With Spark, you find what actually works.
